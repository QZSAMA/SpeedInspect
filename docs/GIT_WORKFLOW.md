# Git 工作流规范

## 🎯 工作流选择
本项目采用 **简化版 GitHub Flow**，适合敏捷开发和快速迭代，同时保证代码质量和可追溯性。

## 📋 分支规范

### 长期分支
| 分支名 | 说明 | 权限 |
|--------|------|------|
| `main` | 生产环境分支，所有正式发布的代码都在这里 | 仅管理员可合并 |
| `dev` | 开发分支，集成分支，最新的开发成果都在这里 | 管理员和开发者可合并PR |

### 短期分支
所有短期分支必须从最新的`dev`分支创建，开发完成后删除。

#### 1. 特性分支 `feature/*`
- **用途**：开发新功能、新特性
- **命名规范**：`feature/功能描述-日期`，例如：
  - `feature/用户注册功能`
  - `feature/AI分析模块优化-20260311`
  - `feature/报告导出PDF`

#### 2. 修复分支 `fix/*`
- **用途**：修复Bug和问题
- **命名规范**：`fix/问题描述`，例如：
  - `fix/登录接口500错误`
  - `fix/前端视频上传失败`
  - `fix/报告计算逻辑错误`

#### 3. 文档分支 `docs/*`
- **用途**：更新文档、注释、README等
- **命名规范**：`docs/更新内容`，例如：
  - `docs/更新API文档`
  - `docs/添加部署指南`

#### 4. 热修复分支 `hotfix/*`
- **用途**：紧急修复生产环境问题，从`main`分支创建
- **命名规范**：`hotfix/问题描述`，例如：
  - `hotfix/生产环境注册失败`
  - `hotfix/支付接口报错`

## 🚀 开发流程

### 1. 开始新功能开发
```bash
# 1. 切换到dev分支并拉取最新代码
git checkout dev
git pull origin dev

# 2. 创建特性分支
git checkout -b feature/你的功能名称
```

### 2. 开发和提交
```bash
# 开发过程中频繁提交小改动
git add .
git commit -m "feat: 添加用户注册功能"

# 提交信息规范：
# feat: 新功能
# fix: 修复Bug
# docs: 文档更新
# style: 代码格式调整（不影响代码逻辑）
# refactor: 代码重构
# test: 测试相关
# chore: 构建/工具/依赖等变动
```

### 3. 提交PR前准备
```bash
# 开发完成后，同步最新的dev分支
git checkout dev
git pull origin dev
git checkout feature/你的功能名称
git rebase dev

# 解决冲突（如果有）
# 运行测试，确保代码正常工作
```

### 4. 提交PR（Pull Request）
1. 推送分支到远程仓库：`git push origin feature/你的功能名称`
2. 在GitHub上创建PR，目标分支选择`dev`
3. PR标题规范：`[类型] 简要描述改动`，例如：
   - `[feat] 实现用户注册和登录功能`
   - `[fix] 修复视频上传失败问题`
4. PR内容需要包含：
   - 改动说明：做了什么，解决了什么问题
   - 测试说明：如何验证功能正常
   - 相关截图（如果是UI改动）

### 5. 代码审查和合并
- 代码所有者进行审查，提出修改意见
- 开发者根据意见修改，提交新的commit
- 审查通过后，由代码所有者合并到`dev`分支
- 合并后删除远程和本地的特性分支

## 🚨 紧急热修复流程
生产环境出现紧急问题需要快速修复：
```bash
# 1. 从main分支创建热修复分支
git checkout main
git pull origin main
git checkout -b hotfix/紧急问题描述

# 2. 修复问题并提交
git add .
git commit -m "hotfix: 修复生产环境注册失败问题"

# 3. 测试验证后提交PR到main分支
# 4. 合并到main后，同步到dev分支
git checkout dev
git merge main
git push origin dev
```

## ❌ 禁止操作
1. ❌ 禁止直接向`main`或`dev`分支提交代码
2. ❌ 禁止在特性分支上合并其他特性分支的代码
3. ❌ 禁止提交不完整的代码或破坏现有功能的代码
4. ❌ 禁止提交敏感信息（密码、密钥、token等）
5. ❌ 禁止强制推送`main`或`dev`分支

## ✅ 最佳实践
1. **小步提交**：每次提交对应一个小改动，便于审查和回滚
2. **提交信息清晰**：其他人能通过提交信息了解改动内容
3. **及时同步**：每天至少同步一次dev分支，避免大冲突
4. **测试充分**：提交PR前确保代码经过充分测试
5. **代码整洁**：遵循项目代码规范，保持代码可读性

## 📝 PR模板
```markdown
## 改动说明
简要描述本次PR做了什么改动，解决了什么问题。

## 改动点
- [ ] 新增功能A
- [ ] 修复Bug B
- [ ] 优化性能C

## 测试说明
如何验证这些改动是正确的？
1. 访问页面xxx，点击按钮yyy，应该看到zzz
2. 调用接口xxx，参数yyy，返回zzz
3. 边缘情况测试说明

## 截图（可选）
如果是UI改动，附上前后对比截图。

## 关联Issue（可选）
关联相关的Issue编号：closes #123
```
